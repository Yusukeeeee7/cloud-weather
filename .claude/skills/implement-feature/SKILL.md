# implement-feature：承認済みの計画を TDD で実装する

## 入力
- 機能番号（例：`3`）と Issue 番号（ブランチ名に使う。なければ止まって聞く）

## 手順

1. **計画を読む**：`docs/plans/<機能番号2桁>-*.md`。
   - 見つからない、または「状態：承認済み」でなければ、**何もせず止まり**、`/plan-feature` を先に実行するよう伝える。
   - 「ブロッカー」が残っていれば止まって知らせる。
2. **読む**：`CLAUDE.md`、計画に書かれたファイル、spec.md の該当節。それ以外は必要になったときだけ読む。
3. **ブランチを作る**：`feature/issues_<issue番号>`（main から）。
4. **Red**：計画のテスト一覧の順にテストを書き、実行して **失敗することを確認し、結果を示して止まる**。
   人間が「実装へ進んで」と言うまで実装しない。
5. **Green**：テストが通る最小限の実装をする。
6. **Refactor**：テストが通る状態を保ったまま整理する。
7. **全チェック**：
   ```bash
   uv run pytest --cov=app --cov=ml
   uv run ruff check . && uv run ruff format --check .
   uv run mypy app ml
   ```
   - 全チェックが通ったら、**実装をわざと壊して、テストが検出するかを確かめる**（境目の比較 `>=`／`>`、条件の `all`／`any`、計画の「内容」に書いた動作を 1 つずつ）。1 か所ずつ壊し、必ず元に戻す。検出しなかったものは、止まって報告する。
   - ワークフローや GitHub の設定の機能（pytest で確かめられないもの）は、わざと検出させる確認用の PR（`feature/issues_<番号>-fail`。マージせずに閉じる）で代える（#53・#54）。
   - ワークフローが外部のサービスのエラーで失敗したときは、成功した実行のログと比べて原因を確かめてから再実行し、再実行したことを記録に書く（#55 の Scorecard）。
8. **計画との差分を記録**：計画から変えた点があれば、計画ファイルの末尾に「## 実装時の変更」として理由と一緒に追記する。
   - 公式ドキュメントで確かめたことは、確かめたその場で、原文を読んだか要約（WebFetch など）を読んだかを書く（spec の表・計画のどちらに書く場合も）。
   - コミット・run・アラートなどの番号は、書く前にコマンドの出力から取り、書いた後に出力と照らす（#54 で、コミットの番号を推測で書いた）。
9. **ドキュメント更新**：spec.md の機能一覧の「状態」を更新。仕様が変わる場合は spec.md にも反映（理由も書く）。
   - spec を書く前に、人間の回答にない変更を一覧にして聞く。「推奨で」などの返事に含まれると、自分で解釈しない。
   - 受け入れ条件のうち、マージ後にしか確かめられないもの（main への push での実行など）があるときは、状態を「実装済み」にし、確かめた後の PR で「完了」にする（#24・#54）。
10. **締め**：結果を要約し、`/review` → PR → `/dev-log` の順に進めるよう伝える。

## ノートブックの機能の場合
- 再利用する処理（特徴量・評価関数）は `ml/` に .py で書き、そちらを TDD で進める。
- ノートブックは上から再実行して通ることを確認する（`uv run pytest --nbmake <ファイル>`）。
- 成果物（data/processed、models、reports）の保存先は spec.md に従う。
- 全期間のデータで実行する前に、ノートブックにも ruff（`ruff check`・`ruff format --check`）を通す（実行した後に直すと、コミットするノートブックが、成果物を作ったものと違ってしまう）。

## 守ること
- 計画にないファイル・機能に手を出さない。必要だと気づいたら、止まって相談する。
- テストを弱める・skip する・期待値を実装に合わせて書き換えることはしない。
- 計画にない依存パッケージを追加しない。
- コミットするときは、計画のファイル一覧にあるファイルを名前で指定して add する（`git add -A` を使わない）。
  一覧にない変更が作業ツリーにあれば、止まって聞く。
