# review：PR 前のセルフレビュー

## 手順

1. `git diff main...HEAD` と変更ファイルの一覧を確認する。対応する機能を `docs/spec.md` で特定する。
2. チェックを実行し、結果をそのまま示す：
   ```bash
   uv run pytest --cov=app --cov=ml
   uv run ruff check . && uv run ruff format --check .
   uv run mypy app ml
   ```
3. 下のチェックリストで差分を確認する。
4. 指摘を重要度別（🔴 必須 / 🟡 推奨 / 🟢 任意）に、ファイル名・行・理由・修正案つきで返す。
5. **自分では修正しない**。人間が修正方針を決めてから直す。

## チェックリスト

**仕様**
- spec.md の受け入れ条件をすべて満たしているか
- spec にない仕様・エンドポイント・項目を追加していないか
- 1つの機能の範囲に収まっているか
- 同じキャッシュ（保存値）を使うエンドポイントを、呼ぶ側（画面など）が同時に呼んでいないか（キャッシュが空のとき、外部APIをそれぞれが呼んでしまう）

**テスト（TDD）**
- 正常系・異常系・境界値があるか（不正な city、タイムアウト、5xx、欠損値、キャッシュ期限切れなど）
- テストが実装の詳細ではなく振る舞いを確かめているか
- テストを弱めた・skip した・期待値を実装に合わせた跡がないか
- 外部APIを実際に呼んでいないか（respx でモック、fixtures を使用）
- 外部の値の検証に、NaN・無限大と単位の場合があるか
- 帯・区間を作る関数は、すべての境目にテストがあるか

**ハルシネーション**
- 外部APIのパラメータ名・レスポンス項目が spec の「確認済み」の表に載っているものだけか
- 存在しないライブラリ関数・引数を使っていないか（不確かなものは実行して確認）
- コメントやドキュメントに、根拠のない数値や説明を書いていないか
- 「公式ドキュメントで確認」と書いた項目は、原文を読んだか、要約を読んだかが書いてあるか
- 文書に写した表は、成果物のファイル（`reports/*.json` など）から行ごとに作り直して比べたか（数値があるかだけの確認は、そう書く）

**セキュリティ**
- シークレット・Webhook URL がコード・ログ・テスト・fixtures に含まれていないか
- 入力検証（city の許可リスト、型・範囲）があるか
- ユーザー入力から URL を組み立てていないか（通信先は spec のホストのみ）
- 外部通信にタイムアウトがあるか
- 追加した依存パッケージは承認済みか
- Dockerfile・Actions を変えた場合：非 root、最小権限、Action のバージョン固定

**ML（該当する場合）**
- 予測時点より後の情報を特徴量に使っていないか（リーク）
- 時系列分割になっているか
- 特徴量作成が `ml/features.py` に集約されているか
- ノートブックが上から再実行できるか、乱数シードが固定されているか
- 成果物（`reports/*.json` など）が変わっていないことは、`git diff` で確かめたか（作業ツリーのファイルのハッシュは、改行の変換で変わることがある）

**品質**
- 型ヒント、関数の大きさ、命名、重複
- 単位（m・℃）と時刻（UTC）の扱い

## 出力の形
```
## レビュー結果：<機能名>
チェック：pytest ✅ / ruff ✅ / mypy ✅ / カバレッジ xx%

🔴 必須
- app/xxx.py:42 … 理由 … 修正案
🟡 推奨
- …
🟢 任意
- …

dev-log に書くべき点（AIの誤りとして記録する候補）
- …
```
