# new-feature：機能を1つ TDD で実装する

## 入力
- spec.md の機能番号（例：`3`）または Issue 番号

## 手順

1. **読む**：`CLAUDE.md`、`docs/spec.md` の該当機能の行と関連する節、既存の関連コードとテストを読む。
2. **確認する**：受け入れ条件が曖昧な点、spec に書かれていないことがあれば、推測せず質問して止まる。
   外部APIの項目が spec の表で「未確認」なら、人間に確認を依頼して止まる。
3. **計画を出す**（ここで必ず承認を待つ）：
   - 変更・追加するファイル
   - 書くテストの一覧（正常系・異常系・境界値）
   - セキュリティ上の注意点（入力検証、シークレット、外部通信）
   - リスクや未決事項
4. **ブランチを作る**：`feat/<issue番号>-<短い名前>`
5. **Red**：テストを書き、実行して **失敗することを確認し、その結果を示す**。
6. **Green**：テストが通る最小限の実装をする。
7. **Refactor**：テストが通る状態を保ったまま整理する。
8. **全チェック**：
   ```bash
   uv run pytest --cov=app --cov=ml
   uv run ruff check . && uv run ruff format --check .
   uv run mypy app ml
   ```
9. **ドキュメント更新**：spec.md の機能一覧の「状態」を更新。仕様の変更があれば spec.md に反映（変更理由も書く）。
10. **締め**：`/review` を実行するよう提案し、その後 `/dev-log` で記録するよう伝える。

## ノートブックの機能の場合
- 再利用する処理（特徴量・評価関数）は `ml/` に .py で書き、そちらを TDD で進める。
- ノートブックは上から再実行して通ることを確認する（`uv run pytest --nbmake <ファイル>`）。
- 成果物（data/processed、models、reports）の保存先は spec.md に従う。

## 守ること
- 1回で1機能だけ。関係ない修正をしたくなったら提案に留める。
- テストを弱める・skip する・期待値を実装に合わせて書き換えることはしない。
- 依存パッケージの追加は理由を説明して承認を得る。
