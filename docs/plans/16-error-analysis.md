### 分析の関数（`ml/error_analysis.py`）

見るのは **正解が上限より下の行**（`target_m < 1524`）。符号は `予測 − 正解`（正なら高すぎ）。

| 関数 | 内容 |
|---|---|
| `height_band(target_m)` | 正解の高さの帯の名前。帯は質問 2。上限の行・正解のない行は欠損 |
| `direction(target_m, predicted_m)` | 行ごとに 4 つのどれか：`at_cap`（予測が上限＝低い天井を見逃した）、`too_high`（上限より下で、正解より高い）、`too_low`（正解より低い）、`exact`（同じ）。上限の行・正解のない行は欠損 |
| `summarize(target_m, predicted_m)` | 上限より下の行について：行数、MAE、符号つきの誤差の平均（偏り）、4 つの向きごとの行数と、誤差の絶対値の合計。行が 0 なら行数 0・ほかは `None` |
| `summarize_by(target_m, predicted_m, keys)` | `keys` の列の組ごとの `summarize` の表（`evaluate.evaluate_by` と同じ形の引数。組を作る列の欠損・行のずれ・予測の欠損は `ValueError`） |
| `ceiling_change(observations, target_m)` | 同じ都市の 1 時間前の正解と比べて：`same`・`lower`・`higher`・`unknown`（1 時間前の行がない・正解がない）。質問 3 |
| `report(observations, target_m, predictions)` | 下の「出すもの」をまとめた、JSON にできる入れ子（小数 2 桁、NaN なし）。`predictions` は名前 → 予測 |

- 誤差の絶対値の合計を出すのは、「見逃した行（`at_cap`）が MAE のうちどれだけを占めるか」を件数と合計から読めるようにするため。割合そのものは書かない（件数と合計から計算できる。#11 の丸めの食い違いを繰り返さない）。
- 入力は書き換えない。

### 案の選び方（結果を見る前に決めておく）

候補は次の 6 つ。#16 で試すことはしない。**下の「選ぶ根拠」に当たる数値が出た案から、最大 3 つを選ぶ**。当たる数値がなければ、3 つに満たなくてよい。表にない案を足すときは、足す前に人間に聞く。

| 案 | 選ぶ根拠（#16 の数値がこうなら） |
|---|---|
| A. 2 段階（上限より下かの分類 ＋ 上限より下の行だけの回帰） | 上限より下の行の誤差の合計の多くを `at_cap`（見逃し）が占める。または、`too_high` に大きく偏っている（上限の行に引っ張られている） |
| B. 概算式からのずれを学習する | 帯の多くで、モデルが概算式より悪い（特定の帯だけでなく全体に負けている） |
| C. 前の時刻の値を特徴量に足す | 1 時間前から正解が変わった行（`lower`・`higher`）の MAE が、変わらない行（`same`）よりはっきり大きい |
| D. 上限より下の行に重みを付ける・目的関数を変える | 特定の帯（とくに低い帯）だけで、モデルが概算式より大きく悪い |
| E. 都市ごとのモデル | 向き・帯の傾向が、2 都市で逆になっている |
| F. 設定の探索 | 上のどれにも当たらない（誤差が一様に大きい） |

- 「多く」「はっきり」「大きく」の線は、ここでは数値にしない（どこに線を引くかの根拠がない）。`model-card.md` には、案ごとに根拠にした数値を並べ、**AI の判断であること** を書く。最後に選ぶのは人間（#17 の計画の承認で決まる）。
- 理由の説明は書かない（「なぜそうなるか」は、分けて数えただけでは分からない。#11 で、数値と合わない推測を書いた）。書くのは「どこで誤差が大きいか」まで。

## リスク・未決事項

- **検証の年は、木の数と学習期間を決めるのに使っている**。検証の年の誤差は、テストの年より少し良く出やすい。`model-card.md` にそう書く。
- **1 年ぶんだけなので、細かく分けると行が少ない**（検証の年の上限より下の行は、東京 1,797・ベルリン 2,875。東京の冬は 282）。都市 × 季節 × 帯では数十行の組が出る。行数を必ず並べ、少ない組の値から案を選ばない。
- **分けて数えても、理由は分からない**。分かるのは「どこで誤差が大きいか」まで。
- **案の根拠の線を数値で決めていない**（上の「案の選び方」）。結果を見てから AI が都合よく読むおそれがある。根拠の数値を並べて、人間が判断できる形にする。
- `ceiling_change` は、正解（METAR）の 1 時間前の値を使う。分析のためだけで、特徴量にはしない（推論のときにない）。案 C で実際に足せるのは、Open-Meteo の前の時刻の値。この 2 つは同じではないので、案 C の根拠としては弱い。
- 学習・評価から除いた行（東京の `BKN///` など）は、今回も見ない（正解がない）。
- 手元で pandas を読み込めるかは日によって違う（2026-10-13 のこのセッションでは読み込めた）。読み込めなければ `Dockerfile.dev` のイメージの中で実行する。

1. **ノートブックと成果物を 1 つずつ足してよいか**：`notebooks/06_error_analysis.ipynb` と `reports/error_analysis.json`。あわせて spec のノートブックの表と、CLAUDE.md の「ディレクトリ」の 1 行に 06 を足す。

3. **spec にない分け方を 2 つ足してよいか**：(a) 現地の時の帯（夜・朝・午後・夕）、(b) 1 時間前からの正解の変化（同じ・下がった・上がった）。

4. **見逃した行を別に数えてよいか**：上限より下の行のうち、モデルが上限と答えた行（`at_cap`。検証の年で東京 227・ベルリン 258）を、「高すぎ」とは別の向きとして数える。
   - 推奨：別に数える。案 A（2 段階）を選ぶかどうかの材料になる。spec の「符号（高すぎ／低すぎ）」より 1 つ細かい。
