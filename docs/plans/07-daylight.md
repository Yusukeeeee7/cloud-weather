spec.md「5. API仕様」`GET /daylight?city=berlin&date=2026-12-21` より（要点）：

> 日の出・日の入りと薄明、昼の長さ・暗い時間を返す。外部APIは使わず、太陽位置の計算で求める。
> `date` は省略時に現地の今日。範囲は 1900-01-01〜2100-12-31。

> - **精度**：Open-Meteo の `sunrise` / `sunset` と比べて ±2 分以内（テストで確認）

設計の要点：

- **計算とAPIを分ける**：`solar.py` は数式だけ（時刻は UTC の `datetime`、角度は度）。`daylight.py` が「現地の日付」と応答の形を受け持つ。
- **「その日の」日の出・日の入りの決め方**（質問 4）：その現地日付の **南中（太陽がいちばん高い時刻）を基準** に、南中より前の通過を朝（sunrise・dawn）、後の通過を夕（sunset・dusk）とする。
  - 南中は対象 2 都市では必ずその現地日付の中にある（東京は現地 11:40 ごろ、ベルリンは 12 時台か 13 時台）。夏時間の切り替え日（1 日が 23 時間・25 時間）でも影響を受けない。
  - 夕方の薄明の終わりが現地の 0 時を過ぎる日がある（ベルリンの初夏の天文薄明など）。その場合も「その日の夕方のもの」として返す（時刻は翌日の現地日付になる）。
- **`null` の扱い**：その高度を一度も通らない日は、朝・夕とも `null`。`solar.py` は「ずっと上」「ずっと下」を区別して返し、時間の計算に使う（質問 6）。
- **時間（hours）の計算**：
  - `daylight_hours` ＝ sunset − sunrise。`night_hours` ＝ 24 − `daylight_hours`（spec のとおり。夏時間の切り替え日も 24 から引く）。
  - `dark_hours` ＝ 24 −（civil の dusk − dawn）（質問 5）。
  - 丸めは小数 2 桁（spec の例 `7.67`）。`solar_noon_elevation_deg` は小数 1 桁（例 `14.2`）。
- **`date` の検証**：`YYYY-MM-DD` だけを受け付け、1900-01-01〜2100-12-31 の範囲を確認する。実在しない日付（`2026-02-30`）、空文字、範囲外は 422 `invalid_date`。
- **「現地の今日」**：`date` 省略時は、時計（UTC）を都市のタイムゾーンに直した日付。タイムゾーンの名前は `app/cities.py` の値（spec 3）。
- **`method`** は固定の文字列 `"noaa-solar-calculator"`。
- 外部通信なし。`/daylight` は Open-Meteo が落ちていても返る。

## 追加する依存パッケージ

| パッケージ | 理由 | 代替案 |
|---|---|---|
| `tzdata` | 「現地の今日」と、テストでの現地日付の確認に、標準ライブラリの `zoneinfo` を使う。Windows にはタイムゾーンのデータがなく、いまは `ZoneInfo("Europe/Berlin")` が失敗する（実行して確認）。Python 公式が配っているデータだけのパッケージで、コードは含まない | (a) UTC との差を固定値で持つ：東京は +9 時間で済むが、ベルリンは夏時間の規則を自分で書くことになり、誤りのもと。(b) 開発用の依存にだけ入れる：Docker（Linux）に OS のデータがあれば本番は足りるが、`python:3.14-slim` にあるかは未確認で、環境で動きが変わる。**推奨は本体の依存に入れる** |

太陽計算のライブラリ（`astral`、`ephem`、`skyfield` など）は使わない。spec が「NOAA の式で計算する」（`method: noaa-solar-calculator`）としているため、標準ライブラリの `math` だけで書く。

## セキュリティ上の注意

- 入力検証：`city` は Enum の許可リスト。`date` は形式（`YYYY-MM-DD`）と範囲（1900-01-01〜2100-12-31）を検証し、外れたら 422。422 の応答に入力値を入れない（今のハンドラと同じ）。
- シークレット：なし。`.env` は読まない。新しい環境変数もない。
- 外部通信（ホスト・タイムアウト）：**アプリからの通信はなし**。fixture の取得（開発時に 1 回）だけが外部と通信する。その通信先・項目は、spec の表で確認済みのものに限る。
- 計算量：1 リクエストの計算は固定の回数（日付の範囲が決まっているので、入力で重くならない）。繰り返しで時刻を求める場合は回数に上限を付ける。
- 数値の安全：`acos` の定義域の外（太陽がその高度に届かない）は例外にせず `None` にする。500 にしない。
- ログ：入力値をそのままログに出さない（検証を通った `city`・`date` だけ）。

### 質問の内容

1. **`city` を省略した場合**：推奨は `/weather` と同じく **`tokyo` として扱う**。空文字は 422 `invalid_city`。
2. **`city` と `date` の両方が不正な場合の code**：エラーの形は code が 1 つだけです。推奨は **`invalid_city`**（エラー表の順。常に同じ結果になるよう固定する）。
3. **時刻の丸め**：spec の例は `:00` ですが、`/weather` の `sunrise` は「丸めずに秒まで返す」と決めています。推奨は **秒まで返す（秒未満は四捨五入）**。分に丸める案もあります（計算の精度が ±1〜2 分なので、秒に意味は薄い）。

6. **`null` のときの時間**：対象 2 都市では日の出入りと市民薄明は毎日あるので API では起きませんが、計算関数としての決まりが要ります。推奨：太陽がずっと上なら `daylight_hours: 24.0`・`dark_hours: 0.0`、ずっと下なら `0.0`・`24.0`。`sunrise`・`sunset` も `null` を許す型にする。

  | Open-Meteo の日の出入り（10 月の 7 日・16 日） | 13 秒 | 6 秒 |
  | Open-Meteo の日の出入り（2025-12-21〜2026-06-21 の 183 日） | 20 秒 | 18 秒 |
  | USNO の薄明（3 種類 × 春分・夏至・冬至。分単位） | 24 秒 | 24 秒 |
  | USNO の南中（分単位） | 26 秒 | 27 秒 |

  USNO の値は分単位（丸めで ±30 秒）なので、差はほぼ丸めの範囲。境目の日（ベルリンの 5 月中旬の天文薄明）も ±2 分に収まり、`None` になる日も USNO の表と一致した。
- **実装**：
  - `solar.py`：スプレッドシートの各列の式をそのまま関数にした。日の出入り・薄明・南中は、南中から始めて「求めた時刻の赤緯・均時差」で 3 回求め直す（スプレッドシートは行ごとの時刻で計算しているため、これで 1 秒以内に合う）。ユリウス世紀は Python の時刻の差から直接出し、スプレッドシートの日付の近似（1901〜2099 年の制限のもと）は使っていない。
  - `date` の検証：実行して確かめたうえで、pydantic の日付の解釈に任せず、半角数字の `YYYY-MM-DD` の形を自前で確かめてから日付にしている。
  - 422 のハンドラ：検証エラーの項目（`loc`）を見て、`date` だけが不正なら `invalid_date`、それ以外は今までどおり `invalid_city`。
  - 日付の範囲（1900-01-01〜2100-12-31）の定数は `solar.py` に置いた（`errors.py` のメッセージと `routers/daylight.py` の検証の両方から使う。`daylight.py` に置くと import が循環するため）。
  - 時計は `/weather` と同じ `app.routers.weather.get_clock` を使っている（置き場所は変えていない）。
