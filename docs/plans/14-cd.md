ワークフローの構成（`cd.yml`）：

- きっかけ：main への `push`（PR のマージで起きる）と、タグの `push`（形式は質問 2）。`pull_request` では動かさない
- `permissions`：ワークフロー全体は `contents: read`。push するジョブだけ `packages: write` を足す（公式ドキュメント「Publishing Docker images」の例で、ghcr.io への push に必要とされている）
- `concurrency`：同じきっかけ（main・タグ）で 1 つずつ実行する。**実行中のものは止めない**（push の途中で止めると、タグが中途半端になるおそれがあるため）
- ジョブは **1 つ**（`cd`、ubuntu-latest、`timeout-minutes` 付き）。#2 と同じく、分けると時間が分単位で切り上げられて増えるため
  1. チェックアウト（`persist-credentials: false`）
  2. `docker build`（ci.yml と同じコマンド。外部 Action を使わない）
  3. `docker run --network none` でコンテナを起動する（外部と通信できない状態。スモークテストの中身を参照）
  4. `scripts/smoke_test.sh` を実行する。起動を待つのはこの中で行う（`/health` が返るまで、上限つきで繰り返す）
  5. 失敗したら、コンテナのログを表示してジョブを失敗にする（push はしない）
  6. ghcr.io にログインする：`docker login ghcr.io --password-stdin` に `GITHUB_TOKEN` を渡す（シークレットをコマンドの引数に書かない）
  7. **手順 2 で作ったイメージに** タグを付けて push する（作り直さない。テストしたものと push するものを同じにする）
- タグの付け方（質問 2）：main への push では `latest` と `sha-<コミットの短いSHA>`。タグの push では、そのタグの名前
- イメージ名は `ghcr.io/<リポジトリの持ち主>/cloud-weather`。持ち主の名前（`Yusukeeeee7`）には大文字があるので、小文字に変えて使う（Docker のイメージ名は小文字だけ、という決まりは実装時に公式ドキュメントで確かめる）
- イメージにリポジトリを示すラベル（`org.opencontainers.image.source`）を付ける。GitHub のパッケージの画面でリポジトリと結び付けるため。`docker build --label` で付け、`Dockerfile` は変えない（ラベルの名前と効果は実装時に公式ドキュメントで確かめる）

スモークテストの中身（`scripts/smoke_test.sh`）：

| # | 問い合わせ | 期待 | 何を確かめるか |
|---|---|---|---|
| 1 | `GET /health` | 200、`{"status":"ok"}` | アプリが起動している |
| 2 | `GET /daylight?city=tokyo` | 200 | ルーターと太陽の計算が動く（計算だけで外部と通信しない） |
| 3 | `GET /cloud-base?city=tokyo` | **502**、`code` が `upstream_error` | モデルが読み込めている。モデルがないと、外部APIを呼ぶ前に 503 `model_unavailable` になる（`app/routers/cloud_base.py`）。`--network none` なので Open-Meteo は呼べず、502 になる |

- 3 の考え方：外部と通信させずに「モデルが読めた」ことを確かめるため、503 ではなく 502 になることを見る。Open-Meteo を実際に呼ぶ確認（200 を見る）は、main のマージのたびに外部を呼び、Open-Meteo の不調で CD が失敗するので採らない（質問 3）。
- 502 になるまでに、リトライの待ち（0.5 秒 → 1.0 秒）と接続の失敗の時間がかかる。`curl` の上限時間はこれより長くとる。
- 応答の JSON は `curl` の出力を文字列で比べる（`jq` などの道具を足さない）。比べ方は実装時に決め、`/health` は本文全体、`/cloud-base` は `upstream_error` を含むかで見る。

**記憶で確定させないもの（実装時に公式ドキュメントで確認し、実行して確かめる）**：
`docker login` に `GITHUB_TOKEN` を渡すときのユーザー名、`packages: write` 以外に要る権限の有無、
初めて push したパッケージの公開範囲（private になるか）とリポジトリとの結び付き、
タグの push のきっかけの書き方、`--network none` で名前解決が失敗したときに httpx がリトライの対象になる例外を出すか（手元の Docker で実行して確かめる）。

## セキュリティ上の注意

- 入力検証：アプリのコードは変えない。ワークフローは、ブランチ名・タグ名・コミットのメッセージなどをシェルの式に直接埋め込まない。タグ名は環境変数で受け取り、イメージのタグとして使う前に形式（質問 2）を確かめる。
- シークレット：使うのは Actions が自動で用意する `GITHUB_TOKEN` だけ。標準入力で `docker login` に渡し、ログに出さない。新しい Secrets は作らない。
- 権限：`packages: write` は push するジョブにだけ付ける。きっかけは main とタグの push だけで、fork からの PR では動かない（`pull_request_target` は使わない）。
- イメージの中身：既存の `Dockerfile` と `.dockerignore` のまま（`.env`・`data/`・`tests/` は入らない）。`models/` は入る。**公開範囲を public にすると、学習済みモデルも誰でも取得できる**（質問 1）。
- 外部通信（ホスト・タイムアウト）：スモークテストの間、コンテナは `--network none` で外部と通信しない。ワークフローは、ビルドで PyPI・Docker Hub・ghcr.io（uv のイメージ）に、push で ghcr.io に接続する。`timeout-minutes` と、スクリプトの待つ上限・`curl` の上限時間を付ける。

## リスク・未決事項

- **確かめられるのはマージの後**：`cd.yml` は main への push で動くので、PR の段階では CI 上で実行されない。マージ後に失敗した場合は、直す PR をもう 1 つ出す（もう 1 回実行される）。
- **ドキュメントだけのマージでも動く**：dev-log だけの PR でも build と push が 1 回ずつ起きる（1 回あたり数分の見込み）。パスで絞ることはできる（push のきっかけなので、#2 のような「必須チェックが動かずマージできない」問題はない）。絞るかは質問 6。
- **イメージが溜まる**：`sha-…` のタグがマージごとに増える（1 つ 631 MB。中身が同じ層は共有されるはず）。ghcr.io の保存量はいまは無料（公式ドキュメント「GitHub Packages の課金」に "currently free"）。有料になったら、古いものを消す仕組みを別の Issue で考える。
- **Actions の消費**：リポジトリは非公開のため、Actions の時間は無料枠（GitHub Free で 2,000 分／月）から引かれる（公式ドキュメント「GitHub Actions の課金」で確認、2026-10-14。WebFetch の要約で確認し、原文は読んでいない。ghcr.io の "currently free" も「GitHub Packages の課金」の要約で確認）。公開すれば無料。
- **uv のバージョン**：`cd.yml` は uv を使わない（`docker build` の中で使うだけ）ので、#2 のような二重管理は増えない。
- **`--network none` での失敗の仕方**：名前解決の失敗がリトライの対象（接続エラー）にならないと、502 ではなく別の結果になる可能性がある。実装の最初に手元で確かめ、違えば質問として戻る。
- **#13 との関係**：#13 は、ここで push した `latest` を使う想定。private のままでも、同じリポジトリのワークフローから `GITHUB_TOKEN` で取得できるかは #13 の計画で確かめる。

## 実装時の変更

- **スモークテストを `scripts/smoke_test.sh`（bash＋curl）から `scripts/smoke_test.py`（標準ライブラリだけ）に替えた**（2026-10-14、人間が承認）。`--network none` で起動したコンテナには、ホストから `-p` のポートで届かなかった（手元の Docker で 60 秒待って届かないことを確かめた）。そこで、同じイメージの別のコンテナを `--network container:<API のコンテナ>` で起動し、その中でスクリプトを実行する形にした。アプリのイメージには curl がないので Python で書いた。新しいイメージも依存も増えない。ruff の対象になり、mypy も手元で `uv run mypy app ml scripts/smoke_test.py` で通した（CI の mypy は `app ml` のままで、`scripts/` は対象外）。
- **`/health` も「本文に含まれるか」で比べる**（計画では本文全体）。3 つの確認をそろえた。本文は `{"status":"ok"}` だけなので、確かめる強さは実質同じ。
- **`--network none` での失敗の仕方を確かめた**：名前解決の失敗は httpx の `ConnectError` になり、リトライ 2 回の後に 502 `upstream_error`（約 1.5 秒）。リスクに書いた「502 にならない可能性」は起きなかった。
- **テスト 3 の「モデルなしのイメージ」は、イメージを作らずに `--tmpfs /app/models` で起動した**（空の tmpfs を重ねてモデルを隠す）。作業ツリーも `Dockerfile` も変えない。
- **ジョブの `permissions` に `contents: read` も書いた**：公式ドキュメント（ワークフローの構文）に「1 つでも指定すると、指定しなかったものは `none` になる」とあるため（WebFetch の要約で確認し、原文は読んでいない）。
- **確かめたこと（公式ドキュメント「Container registry の使い方」、2026-10-14。WebFetch の要約で確認し、原文は読んでいない）**：初めて push したパッケージは private になる。`GITHUB_TOKEN` で push すると、ワークフローのあるリポジトリと自動で結び付く。ラベル `org.opencontainers.image.source` は `docker build --label` でも付けられる。ドキュメントの `docker login` の例は PAT を使うもので、`GITHUB_TOKEN` でのユーザー名は書かれていない。公式の「Docker イメージの公開」の例にならい `github.actor`（環境変数 `GITHUB_ACTOR`）にした。マージ後の実行で確かめる。
- **イメージ名の小文字**：ドキュメントには書かれていなかったが、手元の `docker tag` で大文字の名前は `repository name ... must be lowercase` で拒否された。`${GITHUB_REPOSITORY_OWNER,,}` で小文字にした。
