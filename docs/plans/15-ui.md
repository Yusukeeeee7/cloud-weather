## 内容

### 1. 画面（`GET /`）

- `app/static/index.html`・`app.js`・`style.css` の 3 ファイル。ビルドの道具（npm など）は使わない、素の HTML・JS・CSS。
- `GET /` は `index.html` を返す。JS と CSS は `/static/...` で配る（FastAPI の `StaticFiles`。ファイルの場所はコードの定数）。
- 画面は、ブラウザから既存の API（`/weather`・`/daylight`・`/cloud-base`）と、下の 2 の新しいエンドポイントを呼んで表示する。サーバー側で HTML を組み立てない。
- 表示するもの：
  - 都市の切り替え（`tokyo` / `berlin` の 2 つだけ。許可リストと同じ）。
  - 現在：天気・気温・体感・湿度・風速・雲量。
  - 24 時間の予報：時刻・天気・気温・降水確率・雲量の表。
  - 7 日間：日付・天気・最高／最低・降水確率。
  - 日照：日の出・日の入り・昼の長さ・暗い時間。
  - 雲底：`predicted_m` と `baseline_m` を並べる。`predicted_m` が 1524 のときは「1,524 m より下にシーリングなし」と書く（spec 5 の `/cloud-base`）。503 のときは「モデルを読み込めていません」と出し、ほかの欄は表示を続ける。
  - 過去 24 時間のスライダー（下の 3）。
  - 出典：「Weather data by Open-Meteo.com」と、Open-Meteo へのリンク（CC BY 4.0 で、表示する場所に必要。spec 7）。
- **時刻は表示のときだけ、その都市の現地時刻にする**（CLAUDE.md）。都市のタイムゾーンは `/weather` の `timezone` を使い、ブラウザの `Intl.DateTimeFormat` で変換する。
- どれかの API が失敗したら、その欄だけ「取得できませんでした」と出す（ほかの欄は表示する）。`/weather` の `stale: true` のときは「古いデータ（取得：<時刻>）」と出す。

### 2. 過去 24 時間のデータ（`GET /cloud-history?city=tokyo`）

```json
{
  "city": "tokyo",
  "hourly": [
    {"time": "2026-10-13T04:00:00Z", "cloud_cover": {"total": 70, "low": 50, "mid": 20, "high": 0}}
  ]
}
```

- `hourly` は **24 件**。最後が「現在以前の最も近い正時」（`/cloud-base` の `valid_at` と同じ決め方）、先頭はその 23 時間前。古い順。
- 入力は、`/weather` と同じ 1 回の外部呼び出し（同じキャッシュ `weather:{city}`、同じ TTL・stale の決まり）。
  - その呼び出しに **`past_hours=24&forecast_hours=168`** を加える（2026-10-14 確認済み、spec 7）。`hourly` は 192 行で、先頭は取得時の UTC の正時の 24 時間前（現地の 0 時からではなくなる）。`daily`・`current` は変わらない。
    - 採らなかったもの：`past_days=1` は `daily` も 8 行になり、`/weather` の「7 日分」が壊れる。`past_hours=24` だけでは `hourly` が 408 行（`MAX_HOURLY_ROWS` の 384 を超え、末尾が null）になる。
    - 取得から TTL（15 分）・stale の上限（6 時間）のあいだに使っても、過去 24 時間（取得時の正時の 24 時間前より後）と、`/weather` の先 24 時間（167 時間先まで）は入っている。
  - `/weather` の `hourly`（現在より後の 24 件）と `/cloud-base`（現在以前の正時の 1 行）は、時刻で行を選んでいるので、先頭が前にずれても選ぶ行は変わらない。
- 24 件のどれかの雲量が欠けている・null・時刻が 1 時間おきでない・その時刻の行がない場合は 502 `upstream_error`（`/weather` と同じく、一部だけ返さない）。
- 保存値に過去 24 時間が入っていない場合（このパラメータを足す前に保存された値など）は、キャッシュなしとして外部APIを呼び直す（`/cloud-base` の「保存値が使えない場合」と同じ扱い）。
- 応答に `cached`・`stale`・`fetched_at` は足さない（`/cloud-base` と同じ）。
- `city` の扱い（省略は `tokyo`、空文字・許可リスト外は 422 `invalid_city`）はほかのエンドポイントと同じ。
- 値の意味：Open-Meteo の過去の時間は観測ではなく **過去の予報の保存値**（公式ドキュメントの「archived forecasts」）。画面にもそう書く（「観測値ではありません」）。

### 3. スライダー

- `<input type="range">`（0〜23）で、過去 24 時間の 1 時間ずつを選ぶ。最初は最新（右端）。
- 選んだ時刻（現地時刻）と、全体・低・中・高層の雲量（%）を数字で出す。
- 絵：空を縦に 3 段（上から高・中・低層）に分けた図（SVG）。各段の雲の濃さ（不透明度）を雲量 % に合わせる。スライダーを動かすと絵が変わる。
- 下に、24 時間の小さな折れ線（全体の雲量）を出し、選んでいる時刻に印を付ける。
- 再生ボタンは付けない（spec にない。欲しければ質問 5）。

## 追加：24 時間の予報の雲底（2026-10-14 の人間の指示）

状態：承認済み（2026-10-14。質問 1〜3 は推奨のとおり）

人間の指示：「24 時間の予報で雲底の予測も出したい。この Issue（#31）でよい」。API の返し方は「新しいエンドポイント」（2026-10-14 の回答）。

### 内容

`GET /cloud-base/forecast?city=tokyo`

```json
{
  "city": "tokyo",
  "model_version": "2026-10-13-lgbm-v2",
  "hourly": [
    {"time": "2026-10-14T10:00:00Z", "predicted_m": 850, "baseline_m": 760}
  ]
}
```

- `hourly` は **24 件**で、時刻は `/weather` の `hourly` と同じ（現在より後の最初の正時から。正時ちょうどならその時刻を含む）。画面の 24 時間の予報の表に、同じ時刻の行として並べる。
- 各時刻の予測は `/cloud-base` と同じ作り方：その時刻の `hourly` の 10 項目を、`ml/archive.py` と同じ対応で列の名前を付け、`ml/features.py` の `features` に渡す。24 行をまとめて 1 回で予測する。
  - `predicted_m`・`baseline_m` は、0〜1,524 m に収めた整数（四捨五入。0.5 は切り上げ）。1524 は「それより下にシーリングがない」。`/cloud-base` と同じ。
