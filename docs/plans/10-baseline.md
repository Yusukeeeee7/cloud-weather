### 目的変数の定義（`target_m`）

雲の量は前後の空白を取ってから比べる（`VV ` → `VV`）。知らない値は `ValueError`（`eda.KNOWN_COVERS` と同じ一覧）。

| 行の状態 | `target_m` | spec 9 の決定 |
|---|---|---|
| BKN・OVC・`VV` のうち、高さのある層が 1 つ以上ある | その中で最も低い高さと 1,524 の小さいほう | D1・D2（高さのない層は飛ばす）・D3 |
| BKN・OVC・`VV` の層があるが、どれにも高さがない | 欠損（除く） | D2・D3 |
| BKN・OVC・`VV` の層がない（FEW・SCT・NSC・NCD だけ、または層の報告がない） | 1,524 | D1 |
| METAR が付いていない | 欠損（除く） | D4 |

- `ceiling_m` の列は使わず、雲の層の列（`sky_cover_1〜4`・`sky_height_1_m〜4_m`）と `metar` から作る（`VV` を入れるため）。
- **spec の文と 1 点だけ違いうる所**：`VV` と BKN・OVC が同じ行にある場合。この定義では「3 種類のうち最も低い高さ」になる。`eda.ceiling_status` は BKN・OVC を優先していた。そういう行が全期間に何件あるかをノートブックで数え、0 でなければ報告して止まる（リスク 2）。

### 指標（`evaluate` が返すもの）

| 名前 | 内容 |
|---|---|
| `n` | 評価した行数（`target_m` が欠損でない行） |
| `mae_m` | 全体の MAE |
| `n_below_cap`、`mae_below_cap_m` | 正解が上限より下（`target_m < 1524`）の行だけの件数と MAE |
| `below_cap` の当たり外れ | 正解・予測それぞれが上限より下かどうかの 4 つの件数と、正解率（質問 4） |

- 行が 0 件のとき、MAE と正解率は `None`（エラーにしない。サンプルでは空の分割が出る）。
- 予測に欠損があれば `ValueError`（黙って除かない）。正解と予測の行（index）がそろっていなければ `ValueError`。
- scikit-learn は使わない（pandas だけで書ける。依存を足さない）。

## リスク・未決事項

1. **実装は途中で一度止まる**。(a) 関数とノートブックを作って全期間で実行 → 数値と S1 の推奨を報告 → (b) 人間が成功基準を決める → spec に書く。
2. **`VV` と BKN・OVC が同じ行にある場合**の扱いが、今回の定義と `eda.ceiling_status` で違う。件数が 0 なら影響はない。0 でなければ報告して止まる。
3. **全体の MAE は、上限の行の多さに引っぱられる**（学習期間で「雲が少ない・ない」が東京 41.31%・ベルリン 68.84%）。概算式は晴れた乾いた日に上限に張りつくので、全体の MAE が見かけ上小さくなる可能性がある。成功基準をどの指標で決めるか（全体か、上限より下の行か）が S1 の中心になる。
4. **概算式は東京で形が合わない**（`docs/eda.md` 5 節）。ベースラインが弱すぎると「勝つ」ことに意味がなくなる。参考の予測（質問 1）を並べる理由。
5. **学習と推論の入力の差**：ベースラインは Open-Meteo の過去データ（再解析）で評価する。API は予報で計算する。差の影響は #11 の `model-card.md`。
6. **`eda.py` から関数を移すので、02 のノートブックの結果が変わらないこと**を確かめる必要がある。サンプルの nbmake と、移したテストで確かめる。全期間の出力は作り直さない（コードを変えないため）。
7. **Issue #19 の本文を読めていない**（`gh` がこの環境にない）。spec の機能 #10 と同じ内容という前提。
8. `reports/` を git に入れるのは今回が初めて。`reports/baseline.json` は全期間のデータ（git 管理外）からしか作れないので、CI は中身の正しさを確かめられない（形だけ。テスト 28）。
