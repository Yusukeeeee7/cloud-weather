## リスク・未決事項

- **決定は結果を見るまで書けない**。実装は 2 段階になる：(a) `ml/eda.py` とノートブックを作って全期間で実行 → 結果と推奨を報告 → (b) 人間が D1〜D5 を決める → `docs/eda.md` と spec に書く。(a) の報告で一度止まる。
- **D1・D2 は #10 以降の形を変える**：分類＋回帰なら指標に F1 が加わり（spec 9）、モデルが 2 つになる。D2 で「欠損にする」なら学習に使える正時が減る（東京で最大 1,653）。
- **高さのない層が、特定の時期・時刻に偏っている可能性**（観測の方式が変わった、など）。偏っていれば、学習期間とテスト期間で目的変数の性質が違うことになり、D5 に影響する。原因（観測の方式）はデータからは断定できないので、「偏りがある」という事実だけを書く。
- **サンプル（2 日ぶん）では、ノートブックの大半の集計が意味のある形にならない**。CI が確かめるのは「落ちないこと」だけ。全期間で実行した出力が正しいかは、人間が出力を読んで確かめる。
- **出力つきのノートブックは差分が大きい**（画像を含む）。再実行すると、数値が同じでも画像のバイト列が変わる可能性がある。「同じ結果」は表の数値で確かめる。
- **この PC では pandas を読み込めない**ので、ノートブックを画面で動かしながら試すことができない（Docker の中で一括実行）。図の見た目は、コミット前に人間が VS Code か GitHub の表示で確かめる。
- **`ml/eda.py` の一部（`season`・`local_hour`・露点差）は、#10 の `ml/features.py` で同じものが要る**。#10 で `features.py` に移し、`eda.py` から import する形に直す（今回は `features.py` を作らない。質問 6）。
- **Issue #16 の本文を読めていない**（`gh` がこの環境にない）。spec の機能 #9 と同じ内容という前提。

### 質問の内容

それぞれ推奨を 1 つ書いています。

1. **どの期間を見て決めるか**：推奨は **欠損と件数は全期間、目的変数の分布と特徴量との関係は学習期間（2018〜2023）だけ**。テストの年を見て扱いを決めると、評価が甘くなるため。
2. **決定をコードに反映するのはどこか**：推奨は **#10**（ベースラインの評価には目的変数が要るので、そこで `ml/` に実装する）。#9 は「決めて記録する」まで。#9 に入れると、`ml/metar.py` の変更・parquet の作り直しまで 1 つの PR に入り、大きくなる。
3. **成功基準（spec 9「EDA 後に決め、ここに追記する」）**：推奨は **#10 でベースラインの MAE が出てから決める**。#9 では数値を決めず、`eda.md` に「#10 で決める」と書く。
4. **ノートブックの切り替え**：推奨は **01 と同じ環境変数 `DATA_FETCH_MODE`（`sample`／`full`、既定 `sample`）を使う**。変数を増やさず、CI の設定も変えずに済む。名前は取得用だが、意味（サンプルか全期間か）は同じ。
5. **季節の定義**：推奨は **現地の月で 冬＝12〜2 月、春＝3〜5 月、夏＝6〜8 月、秋＝9〜11 月**（2 都市とも北半球）。spec には定義がないので、決まったら spec 9 に書く（#10 の「季節別」の MAE でも同じ定義を使う）。
6. **`ml/eda.py` を作ること**：推奨は **作る**（決定の根拠になる区分けを、テストのある関数にする）。ノートブックの中だけに書く案もあるが、D2 の件数を数える処理に誤りがあると決定を誤る。
7. **`docs/eda.md` の書き方**：推奨は **AI がノートブックの出力から数値を写して下書きし、決定の欄は人間の回答を書く**。数値を自動で書き出す仕組み（ノートブックから Markdown を生成）は作らない。
8. **分割**：推奨は **分けない**（1 つの PR）。ただし途中で一度止まる（リスクの 1 つ目）。
