ワークフローの構成（`ci.yml`）：

- きっかけ：`pull_request` のみ（push では実行しない。spec 13 の「PR・push」から変更）
- `permissions`：ワークフロー全体で `contents: read` のみ
- `concurrency`：同じ PR で新しい実行が始まったら古い実行を止める
- ジョブは **1 つ**（`ci`、ubuntu-latest）。実行時間はジョブごとに分単位で切り上げて数えられるため、分けずに 1 つにまとめる。必須チェックにはこのジョブ名を指定するので、名前は変えない前提にする
  - チェックアウト → uv の導入 → `uv sync --locked` → `ruff check` → `ruff format --check` → `mypy app ml` → `pytest --cov=app --cov=ml`（80% 未満で失敗）→ `pip-audit` → `docker build`
  - 速く終わるものを先に置く。途中で失敗したら後続（時間のかかる `docker build`）は実行されない
  - `docker build` は push しない。runner に入っている docker コマンドを使い、外部 Action を増やさない
- uv のキャッシュを有効にして、依存のインストール時間を短くする（項目名は実装時に確認）
- `timeout-minutes` を付ける（止まったジョブが実行時間を使い続けないように）
- 外部 Action は `actions/checkout` と uv 公式の導入用 Action の 2 つだけ。コミットの SHA で固定し、コメントに版を書く（更新は Dependabot に任せる）
- Python のバージョンは `.python-version`（3.14）に従わせ、ワークフローに直書きしない
- uv のバージョンは Dockerfile と同じ `0.13.0` に固定する

**記憶で確定させないもの（実装時に公式ドキュメントで確認し、実行して確かめる）**：
uv 導入用 Action の名前・最新バージョン・入力項目、`actions/checkout` の最新バージョン、
`pip-audit` を uv のロックファイルに対して実行する方法、coverage の設定キー名、
`dependabot.yml` の uv 向けの `package-ecosystem` の値。この計画に書いた名前はすべて「候補」。

## テスト一覧（先に書く順）

CI の設定はユニットテストの対象にならない（ワークフローを検証するテスト用ライブラリは追加しない）。
TDD の Red → Green に相当するものとして、**実際の PR での確認シナリオ**を先に決めておく。
確認用のブランチ・PR はマージせずに閉じる（ブランチの削除は人間が行う）。

CI 上で確かめるのは「CI が動く」「失敗するとマージできない」「直すとマージできる」の 3 回だけにする。
各ステップが失敗を検出できることは、CI と同じコマンドをローカルで実行して確かめる（CI を消費しない）。

| # | 確認シナリオ | 場所 | 種類（正常/異常/境界） | 確かめること |
|---|---|---|---|---|
| 1 | カバレッジの下限：テストのない関数を一時的に足して 80% 未満にする | ローカル | 境界 | テストは全件成功しているのに、下限で失敗（終了コードが 0 以外）になる。確認後に元へ戻す |
| 2 | `pip-audit` を実行する | ローカル | 正常 | `uv.lock` の依存に対して実行でき、結果が出る |
| 3 | CI 導入の PR を出す | CI（1 回目） | 正常 | PR で `ci` ジョブが自動実行され、全ステップが成功する |
| 4 | 確認用 PR：テストを 1 件わざと失敗させる | CI（2 回目） | 異常 | `ci` が失敗し、PR がマージできない（ブランチ保護の設定後）。失敗後のステップ（`docker build` など）が実行されていない |
| 5 | 確認用 PR を修正して push し直す | CI（3 回目） | 正常 | 再実行で成功に変わり、マージ可能になる |

- 既存のテスト（`tests/app/test_health.py`）は変更しない。確認用の失敗は確認用ブランチにだけ入れ、この機能のブランチには入れない。
- ruff・mypy・`docker build` の失敗検出は、#1 でローカル確認済みのコマンドをそのまま CI で呼ぶだけなので、CI 上では個別に失敗させない。
- pip-audit の失敗の確認は、脆弱な版をわざと入れる必要があるため行わない。
- main へのマージ後は CI が実行されないことを、Actions の一覧で確認する（追加の実行は発生しない）。

## セキュリティ上の注意

- 入力検証：アプリのコード変更なし。ワークフローは PR のタイトルやブランチ名などの外部入力をシェルコマンドに埋め込まない（スクリプトへの差し込み対策）。
- シークレット：このワークフローはシークレットを一切使わない。きっかけは `pull_request` を使い、`pull_request_target` は使わない（fork からの PR にシークレットや書き込み権限を渡さないため）。
- 権限：`permissions: contents: read` のみ。チェックアウト時に認証情報を作業ディレクトリに残さない設定にする（項目名は実装時に公式ドキュメントで確認）。
- 外部 Action：公式提供元の 2 つに限定し、バージョンを固定する。Dependabot で更新を追う。
- 外部通信（ホスト・タイムアウト）：アプリからの外部通信なし。CI の実行中に PyPI、Docker Hub、ghcr.io（uv のイメージ）、pip-audit が参照する脆弱性データベースに接続する。ジョブに `timeout-minutes` を付ける。
- テストは外部APIを呼ばない（現状どおり）。

- **pip-audit が新しい脆弱性の公表で突然失敗する**：コードを変えていない PR でも CI が赤くなることがある。意図どおりの動作だが、対応方針（依存を更新する／理由を記録して一時的に除外する）は発生時に人間が決める。

- **Python 3.14 の runner 対応**：uv が Python を用意できる想定だが、実際の PR で確認する。
- **改行コード**：ローカルは Windows（`core.autocrlf=true`）、CI は Linux。`ruff format --check` の結果が食い違わないか、最初の PR で確認する。
- **必須チェックの名前**：ブランチ保護はジョブ名で指定するため、後からジョブ名を変えるとマージできなくなる。ジョブ名を変えるときは保護設定も同時に変える。
- **push で実行しないことの影響**：main にマージした後の状態は CI で確かめない。PR のブランチが main より古いままマージすると、組み合わせた結果が未確認になる。ブランチ保護で「マージ前に最新の main を取り込むこと」を必須にすると防げるが、取り込みのたびに CI が 1 回動く。1 人での開発で PR が並行しないため、今回は必須にしない。
- **ドキュメントだけの PR でも CI が動く**：計画や dev-log だけの PR でも 1 回実行される。パスで絞ると必須チェックが実行されずマージできなくなるおそれがあるため入れていない。消費が気になるようになったら、公式ドキュメントで回避方法を確認して別途対応する。
- **Dependabot の PR も CI を動かす**：月 1 回・まとめて 1 PR にして抑える。設定項目の名前は実装時に公式ドキュメントで確認する。
- **ブランチ保護は管理者にも適用する**（2026-10-12 決定）。CI が壊れて誰もマージできなくなった場合は、人間が一時的に保護を外して直す。

## 実装時の変更

- **Action の版と SHA**：`actions/checkout` v7.0.1、`astral-sh/setup-uv` v10.3.0。各リポジトリの README で最新版を確認し、SHA は `git ls-remote --tags` で取得してタグと一致することを確かめた。uv 公式ドキュメントの GitHub Actions ガイドは setup-uv v9.0.0 の例のままだったが、README 側の新しい版を採用した。
- **pip-audit はインストール済みの環境を調べる形にした**（`uv run pip-audit`）：pip-audit 2.10.1 の `--locked` は `uv.lock` を認識しなかった（`no lockfiles found`。実行して確認）。CI では直前に `uv sync --locked` で `uv.lock` どおりの環境を作るため、調べる対象は `uv.lock` の内容と同じになる。dev 依存（pip-audit 自身の依存を含む）も対象に入る。
- **`pip-audit` の追加で間接依存が 24 個増えた**（`pip`、`requests`、`cyclonedx-python-lib` など。すべて dev 側で、Docker イメージには入らない）。初回の結果は「No known vulnerabilities found」。#1 で未確認だった `opentelemetry-api` を含め、既知の脆弱性は報告されなかった。
- **Python の用意**：専用のステップは置かず、`uv sync --locked` に任せた（`.python-version` に従う）。runner 上で 3.14 を用意できるかは、最初の PR で確認する。
- **チェックアウト時に認証情報を残さない設定**：`persist-credentials: false`（`actions/checkout` の README で項目名を確認）。
- **カバレッジの下限**：`[tool.coverage.report]` の `fail_under = 80`。pytest-cov がこの設定に従うことは、シナリオ 1 を再実行して確かめた（71% で `FAIL Required test coverage of 80.0% not reached`、終了コード 1）。
