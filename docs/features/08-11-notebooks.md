# #8〜#11 ノートブック（雲底高度の予測：データ取得 → EDA → ベースライン → 学習 → 評価）

`notebooks/` の 5 つのノートブックをまとめて説明する。機能番号では #8（データ取得）、#9（EDA）、#10（ベースライン）、#11（学習・評価）にあたる。
数値はすべて `reports/*.json`・`docs/eda.md`・`docs/model-card.md`・`docs/dev-log.md` から写したもの。

## 何をするか

空港の上空の「雲の底の高さ（シーリング）」を、天気のデータ（気温・露点・雲量など）から予測するモデルを作り、どのくらい当たるかを測る。
対象は東京（羽田 RJTT）とベルリン（EDDB）の 2 空港、2018〜2025 年の 1 時間ごとのデータ。
結果は「雲が低いかどうかは当てられるが、低いときの高さは昔からある概算式に勝てなかった」で、あらかじめ決めた成功基準には届いていない。

## 仕組み

```
01_data_fetch   METAR（空港の観測）＋ Open-Meteo（過去の気象）を取得し、正時ごとに結合
      │            → data/processed/observations.parquet（140,256 行・28 列）
      ▼
02_eda          データを眺めて、目的変数の決め方・除く行・学習期間を決める
      │            → docs/eda.md（決定 D1〜D5）
      ▼
03_baseline     概算式 125 ×（気温 − 露点）の誤差を測り、成功基準を決める
      │            → reports/baseline.json
      ▼
04_train        LightGBM を学習。学習期間 6 年と 3 年を検証の年で比べる
      │            → models/cloud_base.joblib、reports/training.json
      ▼
05_evaluate     テストの年（2025）で 1 回だけ評価し、成功基準を判定
                   → reports/metrics.json、docs/model-card.md
```

ノートブックは「順に呼ぶだけ」の薄い作りで、中身の処理はすべて `ml/` の `.py` にある（テスト済み）。

関連ファイル：`notebooks/01〜05`、`ml/`（`metar.py`・`archive.py`・`dataset.py`・`raw_store.py`・`eda.py`・`target.py`・`split.py`・`baseline.py`・`features.py`・`train.py`・`model.py`・`evaluate.py`）、`app/clients/`（`iem.py`・`open_meteo_archive.py`・`bulk.py`）、`tests/ml/`、`tests/test_notebooks.py`、`tests/fixtures/data_raw/`

### データ（01）

| | 正解のもと | 入力（特徴量のもと） |
|---|---|---|
| 提供元 | METAR（Iowa Environmental Mesonet） | Open-Meteo の過去データ（再解析） |
| 中身 | 空港で観測した雲の層の量（FEW・SCT・BKN・OVC）と高さ、気温、露点、視程、電文 | 気温、露点、湿度、海面気圧、降水量、雲量（全体・低・中・高）、風速 |

- 期間は 2018-01-01〜2025-12-31（UTC）。1 行 ＝ 都市 × 正時。都市ごとに 70,128 行。
- 結合：正時ごとに、前後 30 分以内で最も近い METAR を 1 つ付ける。
- 単位は摂氏・メートルにそろえる（METAR の華氏・マイル・フィートを変換）。
- 取得した応答はそのまま `data/raw/` に保存し、2 回目からは外部 API を呼ばない。全期間の取得は外部 API 32 回・約 2 分。
- 既定は `sample`（`tests/fixtures/data_raw/` の 2 日ぶん。通信しない）。全期間は `DATA_FETCH_MODE=full` を付けたときだけ。

### EDA で分かったこと・決めたこと（02）

- **「雲が少ない・ない」行がとても多い**（学習期間で東京 41.31%、ベルリン 68.84%）。
- **ベルリンは 1,500 m より高いシーリングをほとんど報告しない**（96.35% が 1,500 m 以下）。東京は 7,000 m まで報告がある。
- 季節の動きが都市で逆：ベルリンは冬に雲が多く低い、東京は夏に多く低い。
- 東京は「BKN・OVC はあるが高さが書かれていない（`BKN///`）」行が 16% ある。「雲がない」とは意味が違う。
- 観測のしかたが途中で変わっている：ベルリンは 2022 年の途中から自動観測、東京は 2023 年から `CAVOK` が約 2 倍。

ここから決めたこと：

- **目的変数 ＝ `min(シーリング, 1524 m)`**。BKN・OVC の層がなければ 1,524 m（5,000 フィート）。つまり「1,524 m」は「それより下にシーリングがない」という意味。
- 正解が分からない行（高さのない BKN・OVC だけ、`VV///`、METAR なし）は学習・評価から除く（全期間で東京 11,403、ベルリン 91）。
- 分割は年で切る：**学習 2018〜2023、検証 2024、テスト 2025**。ランダム分割はしない。

### ベースラインと成功基準（03）

比べる相手は 3 つ。

- `rule_of_thumb`：正式なベースライン。概算式 `125 ×（気温 − 露点）` を 0〜1,524 m に収めた値。
- `always_cap`：参考。何も考えず、いつも 1,524 m と答える。
- `rule_of_thumb_metar`：参考。同じ式を METAR の気温・露点で計算。

検証の年（2024）の MAE（m）：

| | 全体：概算式 | 全体：いつも上限 | 上限より下の行：概算式 | 上限より下の行：いつも上限 |
|---|---|---|---|---|
| 東京 | 712.06 | 201.94 | 371.76 | 818.21 |
| ベルリン | 668.29 | 291.05 | 349.52 | 889.04 |

全体の MAE では「いつも上限」が概算式に大勝ちする（上限の行が多いため）。そこで成功基準を 2 つに分けた。テストの年で、都市ごとに両方：

1. 全体の MAE が「いつも上限」より 10% 以上小さい（＝雲が低いかどうかを当てられる）
2. 上限より下の行だけの MAE が概算式より 10% 以上小さい（＝低いときの高さを当てられる）

### モデル（04）

- 2 都市で 1 つの LightGBM の回帰。目的関数は MAE。
- 特徴量は 17 列（`ml/features.py` の `FEATURE_NAMES`）。Open-Meteo の値 10 列と、計算した 7 列（気温と露点の差、現地の時の sin/cos、年の何日目の sin/cos、太陽高度、都市の番号）。METAR の列は使わない（推論のときにないため）。
- 設定は固定で、探索していない（`learning_rate` 0.05、`num_leaves` 31、`min_data_in_leaf` 20、`seed` 0）。木の数だけを検証の年で決めた（162 本）。
- 学習の行数は 96,620。学習期間を 6 年と 3 年（2021〜2023）で比べ、検証の全体 MAE が 143.99 と 146.98 だったので 6 年のまま。
- 重要度が大きいのは `cloud_cover_low`、`dew_point_spread_c`、`wind_speed_ms` の順。
- 予測は 0〜1,524 m に収める（`ml/model.py` の `predict_m`）。

### 評価（05）

テストの年（2025）の MAE（m）：

| 都市 | 全体：モデル | 全体：いつも上限 | 基準 1 | 上限より下：モデル | 上限より下：概算式 | 基準 2 |
|---|---|---|---|---|---|---|
| 東京 | 114.53 | 174.51 | 満たす（34.37% 小さい） | 408.38 | 378.59 | 満たさない（7.87% 大きい） |
| ベルリン | 147.25 | 254.67 | 満たす（42.18% 小さい） | 410.85 | 407.86 | 満たさない（0.73% 大きい） |

- **成功基準には届かなかった**（2 都市とも基準 2 を満たさない）。
- 「上限より下にあるか」の正解率は、モデルが東京 0.79・ベルリン 0.81、概算式が 0.32・0.37。
- モデルは、正解が上限より下の行の多くを「上限より下」と答えている（東京 1,593 行のうち 1,410 行、ベルリン 2,611 行のうち 2,357 行）。一方、正解が上限の行を「上限より下」と答えた行も多い（東京 1,366 行、ベルリン 1,421 行）。
- 季節別では、上限より下の行の MAE でモデルが概算式より小さいのは、東京の春とベルリンの秋だけ。東京の夏が最も悪い。
- 基準 2 に届かなかった理由は調べていない（未記録）。#16（誤差の分析）で扱う予定。
- この数値は再解析を入力にしたもの。API が使う予報を入力にしたときの精度は測っていない。

## 設計判断

| 判断 | 選んだもの | 他の選択肢 | 理由 |
|---|---|---|---|
| シーリングなしの扱い | 上限 1,524 m で打ち切る | 分類と回帰に分ける | ベルリンは 1,500 m より上をほとんど報告しないので、2 都市で同じ意味になる上限にした。分類＋回帰はモデルと指標が増える |
| 高さのない層（`BKN///`） | 飛ばして次の層を見る。どの層にも高さがなければ除く | 上限の値にする | 飛ばした層は全 1,668 件で、値を決めた層より上にあった（値は変わらない）。高さが分からない行は正解がない |
| 分割 | 年で切る（学習 2018〜2023、検証 2024、テスト 2025） | ランダム分割 | 検証・テストは観測のしかたが変わった後の、いちばん新しい年で、実際の使い方に近い（ランダム分割をしない理由そのものは未記録） |
| 学習期間 | 6 年 | 5 年、3 年 | 年による天気の違いのほうが、観測の変化の前後の差より大きい。3 年とは検証の年で 1 回だけ比べて決めた |
| 成功基準 | 2 つに分ける | 全体の MAE を概算式と比べるだけ | 全体の MAE だけだと、いつも上限と答えるだけで 60% 以上の改善になる |
| 特徴量 | Open-Meteo の値と時刻・都市だけ | METAR の値も使う | METAR は推論のときにない |
| モデルの設定 | 固定。木の数だけ検証の年で決める | 設定の探索 | 検証の年を使う回数を増やさない |
| テストの年を見た後 | モデル・特徴量・成功基準を変えない | 届くまで直す | 直すと、テストの年に合わせたことになる |
| ノートブックの作り | 処理は `ml/` に書き、ノートブックは呼ぶだけ | ノートブックに直接書く | TDD をそのまま使える。学習と推論で同じ関数を使える |
| 生データ | 応答のまま保存し、あれば使う | 毎回取得する | 再実行で外部 API を呼ばない。fixture と本番の読み込みが同じ関数になる |
| モデルのファイル | git に入れる | CI で作る | 学習データが git にないので、CI・CD では作れない |

## テスト

- 何を確かめているか
  - 正常系：METAR の単位の変換、最も近い METAR の結合、目的変数（最も低い層、上限での打ち切り）、特徴量の列の名前と順、MAE と成功基準の判定、モデルの保存と読み込み、学習の再現性（2 回で同じ）。
  - 異常系：壊れた入力・知らない雲の量・足りない列・UTC でない時刻・知らない都市・行のずれ・特徴量の列の順の違いを拒否する。モデルのファイルがない・壊れている場合は `ModelLoadError`。
  - 境界値：結合の 30 分ちょうど、前後が同じ距離、ちょうど 5,000 フィート、改善率ちょうど 10%、UTC の年の境目、季節の月の境目、夏時間の前後。
  - ノートブック：`pytest --nbmake` でサンプルデータを使い、上から通ることを確かめる。`tests/test_notebooks.py` で、出力が残っていないこと（02 だけは残っていること）、手元のパスが入っていないこと、`reports/*.json` の形を確かめる。
- モック・fixtures の使い方
  - 外部 API は `respx` でモック。`tests/fixtures/data_raw/` に 2 都市 × 2 日ぶんの実レスポンスを保存してある。
  - 期待値は、IEM の列ではなく電文そのもの（`BKN005` など）をテストの中で読んで作る（`tests/ml/refs.py`）。
  - MAE や予測の値（何 m）はテストの期待値にしていない。学習のテストは「大小の向き」と「2 回で同じ」だけを見る。
  - 太陽高度の期待値は `app/services/solar.py` を直接呼んだ値（#7 で NOAA の値と照合済み）。
- 実装をわざと壊す確認：#8 で 30 通り（29 検出）、#9 で 21 通り（20 検出）、#10 で 30 通り（すべて検出）、#11 で 12 通り（すべて検出）。
- #11 の終わりの時点で、pytest 996 件成功、カバレッジ 99%。

## セキュリティ・安全性

- シークレットは使っていない（IEM も Open-Meteo の過去データも API キー不要）。
- 通信先は `mesonet.agron.iastate.edu` と `archive-api.open-meteo.com` だけ。タイムアウトは接続 3 秒・全体 60 秒。IEM は 2 秒あけて順に呼び、429 はリトライしない。
- 都市は許可リスト、年は範囲（1940〜2100）で検証し、外れていれば通信しない。生データのファイル名は都市・年から作る（応答の内容からパスを作らない）。
- テスト・CI・サンプル実行は外部 API を呼ばない（サンプルでは、取得の関数を「呼ばれたらエラー」にしてある）。02〜05 の全期間の実行も `--network none`。
- `models/cloud_base.joblib` は pickle 形式で、読み込むとコードを実行できる。読み込むのは、このリポジトリで作って git に入れた決まったパスのファイルだけ。
- 出力を残す 02 と `reports/*.json` は、手元のパスやシークレットらしい文字列がないことをテストで確かめている。
- データの出典を書いている（Open-Meteo は CC BY 4.0、IEM）。

## 面接で聞かれそうな質問と答え

- Q. なぜ全体の MAE だけで評価しなかったのですか。
  A. 目的変数を 1,524 m で打ち切っていて、上限の行が 7 割前後あります。そのため「いつも上限」と答えるだけで全体の MAE が小さくなり、概算式に大きく勝ってしまいます。そこで「雲が低いかどうか」と「低いときの高さ」を別々に見る 2 つの基準にしました。実際、全体の MAE だけなら成功に見えていましたが、2 つ目の基準で概算式に負けていることが分かりました。

- Q. 成功基準に届かなかったのに、なぜモデルを直さなかったのですか。
  A. テストの年の結果を見てから直すと、テストの年に合わせたことになり、数値が信用できなくなるからです。計画の段階で「見た後は変えない」と決めていました。届かなかった結果をそのまま記録し、原因の分析（#16）と改善（#17）を別の機能に分けています。

- Q. 学習と推論でずれが出ないように、何をしましたか。
  A. 特徴量の作成を `ml/features.py` の 1 か所にまとめ、ノートブックと API の両方から同じ関数を呼んでいます。METAR の値は推論のときにないので、特徴量に入れていません。ただし、学習は再解析、推論は予報という入力の違いは残っていて、その差は測れていません。

- Q. ランダム分割にしなかったのはなぜですか。
  A. 記録に残っている理由は、実際の使い方に近づけるためです。API はこれから先の時刻を予測するので、いちばん新しい年（2025）をテストにしました。検証・テストの年はどちらも観測のしかたが変わった後（ベルリンは 100% 自動観測）で、これから予測する相手と同じ条件です。（ランダム分割そのものを避けた理由は、spec には「しない」としか書かれておらず、未記録。）
