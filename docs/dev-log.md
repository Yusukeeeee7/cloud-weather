**学び・CLAUDE.md / skills への反映**
- CI はユニットテストで Red → Green を作れない。「同じコマンドをローカルで実行して失敗を検出できるか確かめる」ことで、CI を消費せずに Red に相当する確認ができた。
- 計画に「候補」と書いておいた項目（pip-audit の実行方法、Action の版）は、実装時に実行・照合して誤りを拾えた。書いていなかった項目（キャッシュ、版の二重管理）は `/review` まで残った。
- 受け入れ条件の中に、リポジトリのファイルでは満たせず GitHub の設定が必要なもの（ブランチ保護）があった。計画の最初に切り分けたことで、何が人間の作業かがはっきりした。
- 変更案（未反映。採用するかは人間が決める）：
  - `plan-feature`：入力の書き方を「機能番号と Issue 番号を両方書く（例：`2 （Issue #2）`）」と明記する。
  - `plan-feature`：計画のテンプレートに「実行のたびに費用・枠を使うもの（CI、外部 API）の回数の見積もり」を加える。
  - `plan-feature` / `implement-feature`：CI やインフラのようにユニットテストを書けない機能の場合の進め方（確認シナリオを決め、ローカルで確かめられるものはローカルで行う）を書く。
  - `review`：手順 1 を、未コミットの変更がある場合は作業ツリーも対象にするよう変える（#1 のログと同じ提案）。
